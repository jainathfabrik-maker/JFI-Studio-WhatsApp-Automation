# Troubleshooting

Find your symptom, then the cause. Every error the app produces names the
variable or the Meta error code involved, and never prints a secret value.

Start with these two calls — they answer most questions immediately:

```bash
curl https://<your-service>.onrender.com/status
curl -H "Authorization: Bearer $ADMIN_TRIGGER_TOKEN" \
     https://<your-service>.onrender.com/admin/diagnostics
```

---

## The service will not start

The process prints a block of `✗` lines naming each variable and where to set
it, then exits 1. That is deliberate: a half-configured service that boots is
worse than one that refuses.

| Message | Fix |
| --- | --- |
| `Missing required variable X` | Set it in Render → Environment. |
| `META_GRAPH_API_VERSION "vXX.X" is not a valid Graph API version` | Use a real version such as `v26.0`. |
| `WHATSAPP_PHONE_NUMBER_ID must be the numeric Phone Number ID` | You pasted the phone number, the WABA ID or the App ID. Use the Phone Number ID from WhatsApp → API Setup. |
| `WHATSAPP_RECIPIENT_NUMBER equals WHATSAPP_SENDER_NUMBER` | Use a different recipient number. Self-messaging is not supported. |
| `No public URL could be determined` (a warning) | Harmless on Render — `RENDER_EXTERNAL_URL` supplies it. Only set `PUBLIC_BASE_URL` for a custom domain. |
| `META_VERIFY_TOKEN must not be the same value as META_ACCESS_TOKEN` | Invent a separate random string. |
| `still contains a placeholder value` | You copied `.env.example` literally. Replace the value. |
| `DAILY_CRON is not a valid cron expression` | `30 8 * * *` is 08:30. Five fields, space separated. |
| `TIMEZONE "..." is not a valid IANA timezone` | Use `Asia/Kolkata`. |

## The Render deploy fails or the service keeps restarting

- **`npm ci` fails with "no package-lock.json"** — commit `package-lock.json`.
  It is generated by `npm install` and should be in the repository.
- **`Cannot find module '/opt/render/project/src/server.js'`** — the repository
  root does not contain `server.js`. Extract the source tree into the root; the
  service cannot run from inside a ZIP.
- **Health check fails** — `/health` must return 200 within Render's timeout.
  If it does not, the process is exiting at startup; read the log for the `✗`
  block above.
- **Node version mismatch** — `package.json` requires Node `>=20.11`.
  `render.yaml` pins `NODE_VERSION=22`.

## The webhook will not verify

Symptom: Meta's **Verify and save** button returns an error.

1. `GET https://<your-service>.onrender.com/webhook?hub.mode=subscribe&hub.verify_token=<YOUR_TOKEN>&hub.challenge=12345`
   should return exactly `12345`. Try it in a browser first.
2. If that returns 403, the token in the URL and `META_VERIFY_TOKEN` differ.
   `/setup` tells you whether a verify token is configured at all.
   Watch for a trailing space when pasting.
3. If it returns 404, the URL path is wrong — it must be `/webhook`, not
   `/webhooks`.
4. If the request never arrives, the service is asleep or the URL is not the
   deployed one. Check `/health` in a browser first.
5. The service logs `Webhook verification succeeded` or
   `Webhook verification rejected` with a reason (`token-mismatch`,
   `wrong-mode`, `challenge-missing`). It never logs the token itself.

## Webhooks arrive but are rejected

Log line: `Webhook rejected: bad signature`.

- `signature-header-missing` — Meta is not sending `x-hub-signature-256`, which
  means the app secret is not configured on Meta's side, or a proxy is stripping
  the header.
- `signature-mismatch` — `META_APP_SECRET` is not the app secret for *this*
  app. Re-copy it from App settings → Basic.
- `app-secret-missing` — `META_APP_SECRET` is not set in Render.

A 401 here is correct behaviour. Meta will retry; fix the secret and the retries
succeed.

## "Refusing to send free-form text"

Symptom: `409`, code `window-closed`.

You are in `WHATSAPP_DELIVERY_MODE=text`, and the recipient has not messaged the
business number in the last 24 hours. WhatsApp only allows free-form messages
inside that window. Two options:

- Switch to `WHATSAPP_DELIVERY_MODE=link` (recommended — it works any time), or
- have the recipient send any message to the business number first.

The app does not quietly convert your text into a template, because that would
mean claiming a delivery path that did not happen.

## Meta error codes you will actually see

The app maps each to a plain-language hint in the log and in the API response.

| Code | Meaning | Fix |
| --- | --- | --- |
| `190` | Access token invalid or expired | Generate a new System User token; update `META_ACCESS_TOKEN`. |
| `100` | A parameter is invalid | Read `error_data.details` in the log — it names the field. |
| `131026` | Recipient cannot receive messages | Number not on WhatsApp, or has not opted in. |
| `131047` | 24-hour window closed | Use `link` mode / an approved template. |
| `132000` | Parameter count does not match the template | Set `WHATSAPP_TEMPLATE_BODY_FIELDS` to match the approved template's variable count. |
| `132001` | Template name or language does not exist | Check `WHATSAPP_TEMPLATE_NAME` and `WHATSAPP_TEMPLATE_LANGUAGE`, and that it is approved. |
| `132005` | Template parameter too long | Each body parameter is capped at 1024 characters. |
| `132007` | Template paused or disabled | Review it in WhatsApp Manager. |
| `132012` | Parameter contains a newline/tab or edge whitespace | Use `link` mode; the pack cannot go into a template parameter. |
| `133010` | Phone number not registered | Finish number setup in WhatsApp Manager. |
| `130429` | Throughput limit reached | The app retries with back-off; slow the schedule if it persists. |
| `131056` | Pair rate limit (too many to one recipient) | Wait; do not increase frequency. |
| `368` | Account temporarily blocked | Review the WhatsApp Business Policy. |
| `80007` | Messaging limit reached | Wait for the 24-hour window to reset; improve quality rating. |

## The daily run does not happen

Check in this order:

1. `GET /status` → `lastRun`. Is there a run today at all?
2. Is `ENABLE_INTERNAL_CRON=true`? If not, nothing runs inside the service —
   you need the GitHub Actions workflow, or a manual `POST /admin/run-daily`.
3. GitHub Actions: open the **Actions** tab and look at the *Daily content pack*
   runs. A red run names the reason. The two usual ones are a missing
   `PUBLIC_BASE_URL` repository variable and a missing `ADMIN_TRIGGER_TOKEN`
   secret — both under Settings → Secrets and variables → Actions.
4. If you use a Render cron job instead, its schedule is **UTC**: `0 3 * * *`
   is 08:30 IST. `30 8 * * *` would fire at 13:30 IST — a very common mistake.
   Its run history shows why it failed; the script exits non-zero with a reason
   such as `PUBLIC_BASE_URL is not set` or `HTTP 401`.
5. Is the web service asleep? A free-tier instance cold-starts on the first
   request; the workflow retries for up to five attempts over about 80 seconds.

## "Skipped: already-sent-today"

Not an error. The run is idempotent per calendar day in `TIMEZONE`. Something
already sent today's pack — a cron job plus a manual call, a restart, or two
instances. This is the guard working.

To deliberately send again, call `POST /admin/run-daily` with
`{"force": true}`. Do not set `force` in a scheduled job.

---

## "Skipped: another-run-in-progress"

A run started less than 15 minutes ago and has not released its lock — usually
because the previous attempt is still in flight or was killed mid-run. Wait 15
minutes, or delete `DATA_DIR/daily.lock`.

---

## A pack was generated but not delivered

Log: `Daily run failed` with a `message`, `code` and `hint`.

The pack is saved with `status: "failed"` and the day is **retryable** — a
failed day is not treated as sent. Fix the cause, then re-run. Nothing was
claimed as delivered.

## The WhatsApp button opens a broken or 404 page

- Open `/setup` and compare the button URL it shows against the one in the
  approved template. They must be identical, with `{{1}}` at the very end.
- If the template was approved against an older host (for example before you
  attached a custom domain), the template itself is wrong and needs re-approval.
  Templates bake the host at creation time; the suffix is the only part that
  varies per send.
- Packs are stored on the service's disk. On a free instance the disk is wiped
  by a redeploy **and** by a spin-down, so the pack file is gone and the link
  shows the "no longer available" page. Attach a Render disk on a paid plan, or
  read the pack soon after it arrives.

## Content quality problems

- **`OpenAI content failed validation`** — the model broke the brief twice. The
  log lists the exact violations. Either re-run (transient), or lower the
  requirements in `validatePack` if a rule is genuinely too strict for your
  taste. The app prefers failing to sending off-brief content.
- **`OpenAI request failed: model not found`** — `OPENAI_MODEL` is wrong or
  retired. Check the current model list and update it.
- **`OpenAI request failed: 401`** — `OPENAI_API_KEY` is wrong, or billing is
  not set up on that API project. A ChatGPT subscription does not include API
  access.
- **Every pack looks the same** — you are on `CONTENT_SOURCE=static`, which is a
  six-pack rotation. Set `OPENAI_API_KEY` and `CONTENT_SOURCE=auto`.

## Logs are hard to read

They are newline-delimited JSON by design, so Render can filter them. In the
Render log viewer, search for `"level":"error"`, `"msg":"Daily run"`, or
`"msg":"WhatsApp delivery status"`. Set `LOG_LEVEL=debug` for full webhook
detail. No secret is ever written to a log line.
